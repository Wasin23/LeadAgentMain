────────────────────────────────────────────────────────────────────────────────
SECTION 1: FULL AGENT FLOW (start to email queued)
────────────────────────────────────────────────────────────────────────────────

This describes the complete lifecycle of one cycle in standard Apollo (non-CRM) mode.

STARTUP (start(), lines 8077–8273)
  1. start() called
  2. Load Zilliz keyword-performance memory → restore industryExhaustion tracker
  3. Load bandit (Thompson Sampling) from DynamoDB → restore keywordSourceAssignments
  4. Call runLoop(), which immediately calls executeReasoningCycle()

CYCLE START (executeReasoningCycle(), lines 8979–9389)
  5. Refresh agent settings from DynamoDB (concurrencyLevel, specialInstructions, etc.)
  6. Reset currentCycle state (leadsProcessed=0, targetLeads=0, phase='search')
  7. If specialInstructions and no campaignPlan yet:
       → Call getUserSettings() to get baseline targeting
       → Call convertInstructionsToPlan() [LLM CALL #1 — gpt-4o-mini]
       → Call generatePlanDescription() [LLM CALL #2 — gpt-4o-mini, ~50 tokens]
  8. Begin the while(stepCount < 5000 && isRunning) loop

MAIN LOOP ITERATION (each step)
  9.  Every 5 steps: checkCreditsStatus() — DynamoDB lookup
  10. Build context object (hasUserSettings, hasEmailSettings, processingPhase, etc.)
  11. Call reason(context) [LLM CALL #3 — gpt-4o-mini, forced function_call]
  12. Translate action to friendly UI message, log to SSE
  13. Call executeFunction(action, parameters)
  14. Call updateCycleState(action, result) — pure state machine, no LLM
  15. If lead_search returned leads AND concurrencyLevel > 1: drainQueueConcurrently()
  16. Loop continues

PHASE: get_user_settings (first iteration or if settings not loaded)
  - executeFunction → getUserSettings() → DynamoDB read (two calls: getLeadAgentSettings + getUserSettings)
  - Stores in memory.userSettings
  - If error: returns shouldStop=true, cycle ends

PHASE: get_email_settings
  - executeFunction → getEmailSettings() → DynamoDB read (getLeadAgentSettings again — same table, same agentId)
  - Stores in memory.emailSettings
  - Note: This is a SECOND call to the same DynamoDB item already fetched by getUserSettings (REDUNDANCY #1)

PHASE: search
  - executeFunction → leadSearch(parameters)
  - Rotates keyword/position (deterministic logic, no LLM)
  - Optionally validates keyword+position pair [LLM CALL #4 — gpt-3.5-turbo, ~80 tokens]
  - After 20 leads/cycle may call generateDynamicTargetPositions() [LLM CALL #5 — gpt-3.5-turbo]
  - After cycling all base keywords: generateRelatedIndustryKeywordsAndPositions() [LLM CALL #6 — gpt-3.5-turbo]
  - Calls Apollo API to search for people (mixed_people/api_search)
  - Enriches each lead via Apollo people/enrich to get email
  - DynamoDB deduplication check (checkForDuplicateContacts)
  - Junk company filter (regex, no LLM)
  - Returns newLeads[], duplicateLeads[]
  - updateCycleState sets processingPhase = 'research', primes currentLead from queue

PHASE: research (for each lead)
  - executeFunction → serperResearch(parameters)
  - Gets agent personality from DynamoDB
  - Runs 2–3 Serper searches (company overview, recent news, optionally LinkedIn)
  - For each non-LinkedIn URL: fetchMultipleWebpages (top 3 URLs per search)
  - For each webpage: [LLM CALL #7 — gpt-4o-mini, insight extraction, ~300 tokens each]
    → Up to ~9 insight extraction calls (3 searches × 3 URLs)
  - For LinkedIn search results: [LLM CALL #8 — gpt-4o-mini, LinkedIn snippet extraction, ~200 tokens]
  - Calls analyzeResearchFindings() [LLM CALL #9 — gpt-4o-mini, research analysis, ~500 tokens]
    → Only runs if there are any contentFindings (the old-format data path)
    → In practice this runs on the fallback path (single search), not the multi-search path
  - Stores allResearchData in memory.lastResearch
  - updateCycleState: if campaignPlan.qualificationCriteria → phase='pre-qualify', else phase='email'

PHASE: pre-qualify (only if campaignPlan has qualificationCriteria)
  - executeFunction → preQualifyLead()
  - Reads memory.lastResearch (organic snippets, top 5)
  - [LLM CALL #10 — gpt-4o-mini, qualification prompt, ~300 tokens out]
  - If score < 20 → SKIP lead, get next from queue or search again
  - If score >= 20 → updateCycleState sets phase='qualify'

PHASE: qualify
  - executeFunction → qualifyLead()
  - Reads memory.lastResearch (citedFacts from webpage extraction)
  - [LLM CALL #11 — gpt-4o-mini, tiered qualification, ~1500 tokens out]
  - Produces: tier (HIGHLY_QUALIFIED/QUALIFIED/SHOTGUN/REJECT), score, reasoning, emailHooks, buyerMotivation, citedEvidence
  - If REJECT: refund credits, rotate keyword, get next lead
  - If qualified: stores memory.currentQualification with full aiReport
  - updateCycleState: if lead has email → phase='build', else phase='email'

PHASE: email (unlock email if not already present)
  - executeFunction → unlockEmail(parameters)
  - Apollo search (mixed_people/api_search) by person name + domain/company
  - Apollo enrich (people/enrich) to get actual email
  - ZeroBounce validation (non-blocking, rejects only spamtrap/do_not_mail)
  - updateCycleState: phase='build' if success, or skip lead if failure

PHASE: build
  - executeFunction → buildPersonalizedEmail()
  - First runs runSupportingResearch() if not already done:
    → Checks Zilliz RAG for industry facts
    → Serper search for industry statistics [LLM CALL #12 — gpt-4o-mini, industry stats extraction]
    → Serper search for user company wins [LLM CALL #13 — gpt-4o-mini, company wins extraction]
    → Each with up to 3 URL fetches + insight extraction calls
  - Queries Zilliz RAG for relevant facts (queryRelevantFacts)
  - If useTemplates=true: fills merge tags, optionally generates subject [LLM CALL #14 — gpt-4o-mini]
  - If AI mode (default):
    → [LLM CALL #15 — gpt-4o (full model), Sales Strategist reasoning, ~900 tokens out]
    → Mistral email generation [LLM CALL #16 — mistral-medium-latest, ~300 tokens out]
    → Optionally subject line generation if strategist didn't produce one [LLM CALL #17 — gpt-4o-mini]
    → [LLM CALL #18 — gpt-4o-mini, lead confidence analysis, ~200 tokens out]
  - Appends unsubscribe footer
  - Returns { success, email body, subject, confidenceReport, confidenceLevel, salesAngle }
  - updateCycleState: leadsProcessed++, get next lead, phase='research' or 'search' or 'complete'

POST-EMAIL
  - addToEmailQueue() called from updateCycleState
  - Stores to DynamoDB email queue
  - Tracks contact in contactedLeads DB (addContactedLead)
  - Optional CRM sync (syncLeadToCRMUnified or addNoteToExistingCRMContact)
  - Broadcasts SSE events to frontend

CYCLE END
  - When processingPhase='complete' or stepCount>=5000 or empty searches >= 8
  - logCycleCompletion to DynamoDB
  - runLoop schedules next cycle via setTimeout (default 30 minutes)

LLM CALL #1: reason() — The Main Orchestration Call
Lines: 1096–1369
Function: reason(context)
Model: gpt-4o-mini
════════════════════════════════════════════════════════════════════════

PURPOSE: Decide which tool/function to call next in the agent loop.

PROMPT SIZE:
  Input: ~150 tokens (comment at line 1095 claims "61% savings" from 700→150 tokens)
  The prompt is:
    "Lead agent cycle decision:
     STATUS:
     Settings: ✓/✗ | Email templates: ✓/✗
     Progress: X/Y | Phase: <phase>
     Lead: <name> (<company>, domain: <domain>)
     Complete: <bool>
     Call the appropriate function to continue the workflow."
  Then the full tools[] array is passed as OpenAI function definitions.
  The tools[] array adds ~300–500 tokens in schema overhead.
  Total: roughly 450–700 tokens per call.

CONTEXT PASSED:
  - Whether user/email settings are loaded (booleans)
  - leads processed / target leads
  - processingPhase ('search', 'research', 'pre-qualify', 'qualify', 'email', 'build', 'complete')
  - currentLead name/company/domain (if active)
  - cycleComplete (bool)

WHAT IT'S DECIDING:
  Which of 7 tools to call:
    get_user_settings, get_email_settings, lead_search, serper_research,
    unlock_email, build_personalized_email, pre_qualify_lead, qualify_lead

COULD THIS BE HARDCODED?
  YES. Almost completely. See determineFunctionCall() at lines 1372–1433,
  which already hardcodes the exact same logic as a fallback:
    - No user settings → get_user_settings
    - No email settings → get_email_settings
    - cycleComplete → 'none'
    - phase='search' + no lead + empty queue → lead_search
    - phase='pre-qualify' + lead → pre_qualify_lead
    - phase='research' + lead → serper_research
    - phase='qualify' + lead → qualify_lead
    - phase='email' + lead + no email → unlock_email
    - phase='email' + lead + email → build_personalized_email
    - phase='build' + lead → build_personalized_email

  The LLM is called AFTER determineFunctionCall() builds the forced function_call
  parameter, so the LLM is ALREADY forced to call a specific function. It only
  provides "reasoning" text in message.content. The actual decision is hardcoded.

GENUINELY BRANCHES? NO.
  The function_call parameter is passed as { name: 'specific_tool' } or 'auto'.
  When forced, the LLM cannot deviate. The only time 'auto' is returned is when
  processingPhase is 'paused' or cycleComplete=true — and in those cases the
  loop already breaks before reason() would have a meaningful effect.

WHAT HAPPENS IN EACH BRANCH:
  Always calls the same function that determineFunctionCall() would return.
  The only "branch" is the error fallback (lines 1281–1368) when OpenAI is rate-
  limited — which runs identical deterministic logic.

REMOVING IT WOULD BREAK ANYTHING?
  No. You could replace reason() entirely with determineFunctionCall() + a direct
  call to executeFunction(). The LLM adds:
    - A human-readable "reasoning" string logged to console/UI
    - Parameters for lead_search (query, companySize, location, industries, position)
      BUT the parameters are mostly ignored because leadSearch() uses its own internal
      keyword rotation and position selection logic, not the GPT-provided parameters.

  VERDICT: This call costs money every cycle step (~6–8 calls per lead processed)
  for zero decision-making value. The entire reason() function could be replaced
  by a 30-line deterministic router with no loss of functionality. This is the
  single largest optimization opportunity in the file.

ESTIMATED CALLS PER LEAD: ~6–8 (settings load ×2, search ×1, research ×1,
  pre-qualify ×1, qualify ×1, email-unlock ×1, build-email ×1)
COST: ~4,000–6,000 tokens per lead at gpt-4o-mini pricing.

REDUNDANCY #1: Double DynamoDB read for user settings
  getUserSettings() (lines 2284–2336) calls BOTH:

  So when the agent starts a cycle, it calls getLeadAgentSettings TWICE in succession.
  The two calls are to the same DynamoDB table, same agentId. The second call is entirely
  redundant. Fix: cache the result of getLeadAgentSettings in the first call and pass
  it to getEmailSettings. Or merge getUserSettings + getEmailSettings into one call.

  executeReasoningCycle() also calls getUserSettings() separately at lines 9060–9062
  to get tempSettings for convertInstructionsToPlan, making a THIRD call to the same
  DynamoDB item before the main loop even starts.

REDUNDANCY #2: Apollo enrichment in leadSearch duplicated in unlockEmail
  During leadSearch() (lines 5870–5938), EVERY lead with has_email=true is:
    (a) Found via mixed_people/api_search
    (b) Immediately enriched via people/enrich to get the actual email address

  Then, if the enriched email is somehow null or missing, the agent later runs
  unlockEmail() (phase='email'), which:
    (a) Searches AGAIN via mixed_people/api_search for the same person
    (b) Enriches AGAIN via people/enrich

  This double-enrichment shouldn't happen in the happy path (leadSearch already
  sets lead.email, so updateCycleState at line 1671 jumps to phase='build' not 'email').
  But if leadSearch enrichment yields no email and the lead still passes dedup,
  unlockEmail runs a second search+enrich cycle.

  The leadSearch enrichment also always enriches every lead it finds, even ones that
  will be disqualified and never emailed. This wastes Apollo credits on research-phase
  leads that get REJECTed. Consider moving enrichment to after qualification.

REDUNDANCY #3: Research called twice per lead in concurrent processLeadPipeline
  processLeadPipeline() (lines 7845–8013) is the concurrent path (concurrencyLevel > 1).
  It calls qualifyLead() directly (line 7884) without checking if pre-qualification
  should run first. This means concurrent mode skips preQualifyLead entirely — it goes
  straight to the expensive qualifyLead() call regardless of whether the lead should
  be screened first. The sequential path does pre-qualify → qualify as two separate gates.

REDUNDANCY #4: memory.lastResearch written twice in serperResearch
  serperResearch() sets memory.lastResearch at:
    line 3387: this.memory.lastResearch = allResearchData;  (during search loop)
    line 3552: this.memory.lastResearch = researchResults;  (final return object)
  The second assignment is to the same data wrapped with additional fields. This is not
  a logic bug but is confusing and slightly wasteful.

REDUNDANCY #5: analysisPrompt for research analysis only fires on fallback path
  analyzeResearchFindings() at lines 3519–3535 is only called when there are
  contentFindings (from the old data format — answerBox, knowledge graph, organic snippets).
  In the multi-search path (when campaignPlan exists), contentFindings is usually empty

REDUNDANCY #6: DynamoDB user lookup in addToEmailQueue
  addToEmailQueue() at lines 7725–7729 calls awsManager.getUserById() to check if

SECTION 6: OTHER NOTABLE FINDINGS
────────────────────────────────────────────────────────────────────────────────

FINDING 1: Dead Anthropic SDK
  Lines 15, 59–61: Anthropic SDK is imported and instantiated but never used.
  this.anthropic is initialized but no call to this.anthropic.* exists anywhere in the file.
  Remove the import and constructor assignment.

FINDING 2: findLeads() is an alternate agent loop that's likely unused
  Lines 6631–6892: findLeads() is a completely separate execution loop that predates the
  current executeReasoningCycle() pattern. It has its own while loop, duplicate research
  and qualification calls, etc. It is likely not called by any route handler.
  Verify and potentially remove this dead code path.

FINDING 3: extractBusinessType(), extractKeyServices(), extractCompanyDetailsFromResearch(),
  extractSpecificInsights(), calculateSimilarity(), extractCompetitivePosition(),
  extractTechnologyStack(), assessResearchQuality() at lines 2067–7449
  These are all pure-JS regex/pattern-matching functions used in addToEmailQueue() to
  build the researchData object stored with each queued email. None of them affect
  email generation directly. They add metadata to the queue record for the UI.
  The output of extractSpecificInsights() in particular is large and complex. Verify
  it's actually used by the frontend (it might just be stored and never displayed).

FINDING 4: Stop signal race condition
  The check `if (!this.isRunning) break;` appears in 3 places in the while loop
  (lines 9142, 9210, 9238), but between them are async LLM calls that take 1–5 seconds.
  A stop() call during an LLM call won't take effect until the next check. This is
  acceptable for a JS async system but means the agent may complete one more step after stop().

FINDING 5: templateMode bypasses all research, qualification, and strategist
  If useTemplates=true (lines 4458–4533), the flow is:
    → Fill merge tags in template body
    → Optionally generate subject
    → Return immediately
  No research, no qualification, no strategist call. The buyerMotivation GATE at
  lines 4406–4443 is also bypassed (template mode exits before the gate check).
  So template mode sends emails to any lead regardless of qualification. This may
  be intentional but is a significant behavioral difference from AI mode.

FINDING 6: Concurrent mode (concurrencyLevel > 1) skips pre-qualification
  processLeadPipeline() calls serperResearch → qualifyLead directly.
  The pre-qualification phase (preQualifyLead) is absent. Sequential mode runs:
  research → pre-qualify → qualify. Concurrent mode runs: research → qualify.
  This inconsistency means concurrent mode does an extra qualifyLead() call that
  preQualifyLead() would have prevented for low-scoring leads.

FINDING 7: Apollo enrichment happens during search, wasting credits on rejected leads
  leadSearch() enriches every lead immediately (people/enrich) to get emails.
  If 10 leads are returned but 7 are later rejected by qualifyLead(), those 7 enrichment
  credits were wasted. Moving enrichment to after qualification would save Apollo credits.
  The current structure is: search → enrich all → dedup → qualify → (if qualified) use email.
  Better: search → dedup → qualify → (if qualified) enrich for email.
  Note: The `has_email` flag on Apollo search results indicates availability without
  revealing the email, so enrichment can be deferred.

FINDING 8: Bandit (Thompson Sampling) is functional but single-source in practice
  The LeadSourceBandit is fully implemented and the code paths for multi-source switching
  are all live. However, getAvailableSources() from leadSourceRegistry.js almost certainly
  returns only Apollo in a standard deployment. The bandit logic adds overhead per search
  (bandit.select, bandit.reward, bandit.flushToDB) that is effectively a no-op until a
  second source is registered. This is future-proofing, not current waste.

FINDING 9: Memory/Zilliz integration is non-blocking
  leadMemory.storeKeywordPerformance() at line 6083 and industryFacts.upsertFacts() at
  line 3869 are awaited inside the main loop, which means a Zilliz write failure causes
  error logging but is caught and ignored. Good. But they DO add latency (network call)
  to each search and supporting research cycle.

FINDING 10: The safety limit maxSteps=5000 (line 9122) could loop for hours
  Each step includes an LLM call (reason()) + at least one async action.
  At 2–5 seconds per step, 5000 steps = 2.7–13.8 hours of continuous operation.
  This is probably intentional for high-volume campaigns but should be verified.
  The actual exit conditions (cycleComplete, empty searches >= 8) fire much sooner.
